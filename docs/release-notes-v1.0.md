# Version 1.0 Release Notes

Release date: 2026-07-20

## Overview

Version 1.0 is the first baseline release of the NPB Archive Chat AI.

It is an AI chat experience that uses saved NPB official game data to search, analyze, and explain professional baseball records in natural language. The system is designed as a data-grounded baseball commentator: it answers from canonical data when it can, explains uncertainty when it cannot, and routes news or realtime questions away from unsupported generation.

## Main Capabilities

- Natural language search for NPB games, players, teams, events, lineups, batting lines, pitching lines, and season aggregates.
- Player, team, season, and game analysis using stored NPB records.
- Historical record answers for past games, past seasons, comparisons, rankings, and record-style questions.
- Capability routing for `historical_record`, `analytical`, `opinion`, `news`, and `realtime` questions.
- Data-grounded opinion answers that are generated only after repository-backed analysis.
- Game detail answers with mobile-readable sections and automatic game highlight summaries.
- Direct answer presentation for first-record and ordinal-record questions such as first home runs.
- Context-aware follow-up question suggestions generated by templates, not by free-form LLM output.
- News and realtime capability failure templates that direct users to Sports Navi NPB: https://baseball.yahoo.co.jp/npb/

## Improvements Included in 1.0

- Normalized D1 is the production runtime contract.
- Legacy runtime fallback and request-time live fetch paths are retired.
- QA-specific hardcoded answer bypasses are removed.
- Repository boundaries return stable domain shapes to the web layer.
- Summary text starts with the answer to the user's question rather than a raw result count.
- Game detail output is organized for smartphone reading: result, scoring, pitchers, batters, and key scoring scenes.
- Game highlights summarize what happened in the game before listing details.
- Follow-up suggestions inherit the current entity and avoid unsupported news/realtime topics.

## Phase History

### Phase 5: Normalized Production Hardening

Production runtime was fixed to normalized D1. Legacy DB access was restricted to rollback and conversion use. Daily update guards, capacity monitoring, duplicate/orphan checks, and normalized-only runtime checks were added.

### Phase 5.1: QA Bypass Retirement

QA-specific hardcoded answer paths and recovery branches were removed. Error boundaries, identity handling, repository error contracts, and QA path observability were hardened.

### Phase 6: Conversation & Capability Architecture

Questions were classified into historical, analytical, opinion, news, and realtime capabilities. News and realtime questions were routed to external source guidance rather than generated from the DB.

### Phase 7: Answer Presentation Improvement

Answer structure was improved without changing data retrieval. Direct-answer summaries, mobile-readable game details, and more useful game detail card titles were added.

### Phase 8: Game Summary Highlight Generation

Game detail answers gained data-derived highlight summaries that identify pitching battles, close games, see-saw games, one-sided games, comeback shapes, walk-off moments, and key events.

### Phase 9: Context-aware Follow-up Suggestions

The response schema gained `suggested_questions`. Related questions are generated from templates using intent, capability route, entity, answer mode, and result shape. Suggestions are displayed at the end of the answer and avoid unsupported news/realtime topics.

## Known Limitations

- The system does not provide news delivery.
- The system does not provide realtime game status, live scores, lineups, or in-game play-by-play.
- The system does not answer injury, registration, contract, transfer, trade, or comment questions from stored DB data.
- The system does not make unsupported future predictions.
- The system does not infer coaching intent, team strategy, player condition, or private context without data.
- The system does not use SNS, article text, or unsaved external web pages as answer evidence.
- If canonical data is missing, the answer must say so instead of filling the gap with speculation.

## Design Principles

- Prioritize correctness over fluency.
- Use saved canonical NPB data as the evidence boundary.
- Separate data-derived facts from commentary and opinion.
- Do not let the LLM freely invent capabilities, facts, or related questions.
- Keep Planner, Repository, Answer Generator, Highlight Generator, and Follow-up Generator responsibilities separate.
- Put UX improvements in the generator and presentation layers when possible.
- Preserve normalized-only runtime behavior.
- Do not reintroduce legacy fallback or request-time live fetch into normal chat answers.
- For unsupported capabilities, guide the user to an appropriate source instead of fabricating an answer.
