# Acceptance Test 正本 — ブラックボックス型ユースケーステスト（2026-08-28実施）

> ステータス: 正式な受入テスト。単発33件と複数ターン14件の計47ターンをケース／ターン単位で判定する。
> Release Ready条件: 本Acceptance Test 47/47 Pass、かつ `docs/qa-test-cases.md` の実装回帰テスト182/182 Pass。
> 初回記録の回答と判定は監査証跡として保持し、期待値として固定しない。QA正本や事実関係と矛盾する初回判定は `QA仕様` として是正する。

## 目的・前提

このドキュメントは、本リポジトリのAIチャット機能に対して実施したブラックボックス型のユースケーステストの結果記録である。

テスト設計にあたり、事前に知ってよい情報として使用したのは以下の2点のみ。

- このAIチャットは、NPBの試合結果・選手成績などをもとに質問へ回答するチャットである
- 参照可能な情報は、昨日終了時点までが最新である

既存QAケース（`docs/qa-test-cases.md`）・QA結果・仕様書・Planner/Repository等の実装詳細は、質問設計や期待値の根拠として使用していない。実行方法（起動コマンド、`POST /api/chat` のリクエスト形式）を特定するためだけに、`README.md`・`docs/getting-started.md`・`packages/schemas/src/index.ts` のリクエスト/レスポンス型定義（`message`/`history`/`answer.summary` などのフィールド名のみ）を最小限確認した。これらは質問内容や期待回答には反映していない。

## 実行環境・実行方法

- ローカル起動: `NPB_SQLITE_PATH=data/npb-2025.sqlite` / `NPB_SQLITE_DIR=data` を指定し `pnpm dev`（Nuxt dev server, `http://127.0.0.1:3000`）
- 実行手段: `POST /api/chat` に `X-NPB-User-Id` ヘッダ（ケースごとに別IDを使用）と `{"message": ...}` （複数ターンでは `history` 配列も付与）を送信し、実際のレスポンスを取得
- 各ケースは実際にAPIを呼び出して取得したレスポンスの `answer.summary` フィールド（チャットUIの回答本文に相当）をそのまま記録している。長大な `source_urls` 一覧は件数のみ記載し、本文（`summary`）は要約・改変せずそのまま転記した。

### テスト環境のデータ範囲に関する注記（重要な前提のずれ）

事前情報として「参照可能な情報は昨日終了時点（2026-08-27）までが最新」と伝えられていたが、事実確認のためローカルDB（`data/npb-2026.sqlite`）を直接確認したところ、実際に格納されている試合データは **2026-03-14〜2026-07-31** までであり、8月のデータは存在しなかった。これはローカル開発環境のデータ更新が止まっていることによるものと考えられ、本番環境のデータ鮮度とは無関係の可能性がある。そのため「昨日の試合結果が返ってこない」ケース（B01等）は、本番の仕様不備というより、このテスト環境のデータ欠落による可能性がある点を評価に反映した（該当ケースでは判定理由に明記する）。この事実確認はDBへの直接クエリのみで行っており、AIチャット本体のソースコード（Planner等）は参照していない。

### B01
**質問**: 昨日の巨人の試合結果を教えて

**実際の回答**:
```
条件に一致する試合は見つかりませんでした。
```

**判定**: Partial

**判定理由**: 「見つからない」こと自体は（このテスト環境のDBが7/31までしかデータを持たないため）結果として誤りではないが、なぜ見つからないのか（対象日に試合がなかったのか、データが存在しないのか）が一切説明されず、ユーザーは原因を判断できない。

**気になった点**: 前提の「昨日まで」を額面通り信じたユーザーが見たら「今日日付の巨人戦データがまだ入っていない不具合」と誤解しかねない。少なくとも「その日程のデータが見つからない」旨をもう少し丁寧に伝えるべき。

### 件数・Pass率

単発質問とマルチターンの内訳:
- 単発質問: 33件（Pass 2 / Partial 1 / Fail 30）
- 複数ターン会話: 5会話・14ターン（Pass 0 / Partial 1 / Fail 13）

### 主な失敗パターン

1. **「イベントです。該当数:◯件」という汎用の非回答**（B03, B05, B10, B14〜B19, B21, B24〜B26, B30, B33, MT01全ターン, MT02-Turn2等、非常に多数）。質問内容にかかわらず、条件抽出に失敗すると内容不明の過去イベント一覧を無条件に返す、というフォールバック的挙動が疑われる。
2. **質問された選手とは無関係な選手・無関係な試合が返る**（B09, B11, B13, B29, MT03-Turn2/3, MT04全ターン, MT05全ターン）。しかも軒並み2016年前後の、データ中最も古い時期の記録が選ばれる傾向が強く、「該当なし→フィルタなしの先頭行を返す」ような処理になっている可能性が疑われる。
3. **ランキング・集計の数値そのものが誤り、または断定的に誤情報を提示**（B06, B07, B22）。本塁打数でソートされていない、打率が1を超える、セ・リーグ指定なのにパ・リーグ選手が混在するなど、複合的な事実性の誤りがある。
4. **フォローアップで直前の文脈（チーム名・選手名・対象試合）が失われる**（MT01, MT02, MT03-Turn2/3, MT05-Turn2/3）。指示語（「その試合」「その投手」「二人だと」等）を用いた自然な会話がほぼ機能していない。
5. **「対応できません」という誠実な回答が一部の質問にしか出ない**（B02のみ明確に成功。B03, B15, B17, B24, B33等、同種のスコープ外・未来予測質問は無関係データの羅列で応答一貫性がない）。

### Partialになった主な理由

- B01: 「見つからない」こと自体は結果として妥当だが、理由の説明がなく不親切。
- MT03-Turn1: 実在するデータで詳細な回答ができている点は良いが、要求されたカード（巨人対阪神）が存在しないことを明示せず、別カードの結果を差し替えて出している点が問題。

### 実利用上のリスクが大きい問題

- **誤ったランキング・誤った数値を断定的に提示する**（B06, B07, B22）ことが最大のリスク。ユーザーが検証せずに信じた場合、誤った知識（例:「セ・リーグの本塁打王は宮﨑」等、実際には正しくない可能性が高い順位）を持ち帰ってしまう。
- **無関係な選手の古いデータを、あたかも「直近」「最近」の情報であるかのような文面で提示する**（B09, B11, B29等）。「最後の出場から◯日空いています」という免責文言が付くケースはまだ良心的だが、それすらないケース（B29等）もある。
- **存在しないカード・試合を、あたかも要求通りの結果であるかのように断りなく差し替えて提示する**（MT03-Turn1）。ユーザーが誤読すると、事実と異なる対戦カード・スコアを記憶してしまう。

### 曖昧な入力で問題になったパターン

- B14（「この前のカード」、チーム名なし）、B21（「さっき言ってた選手」、実際には文脈が存在しない）のいずれも、聞き返す・確認するという対応が一度も取られず、無関係データで押し切られた。特にB21は、文脈が存在しないにもかかわらず特定の選手名（長野）を提案質問に登場させており、「根拠なく対象を決めつける」ことに近い挙動が見られた。
- B27（「タイガーズ」という球団の言い方の揺れ）、B31（「田中選手」の「選手」という敬称）は、いずれも本来はチーム／複数候補として正しく処理できてよいはずが、存在しない「選手名」として厳密一致検索され、not_found という誤解を招く結果になった。

### follow-upで問題になったパターン

- MT01, MT02, MT03（Turn2以降）, MT05（Turn2以降）のいずれも、直前のターンで確立された主語（チーム・選手・試合）を引き継げていない。特にMT03のTurn2/3は、直前に提示した具体的な試合（巨人×ソフトバンク）を無視し、日付だけが一致する全く別の試合（広島×ロッテ）を返しており、フォローアップとして機能していないことが明確に確認できた。
- 「じゃあ〜は？」のような省略混じりの言い換え（MT05-Turn2）も、主語の補完に失敗していた。

### 事実性で問題になったパターン

- B06, B07, B22: ホームラン数でソートされていないランキング、打率が1を超える異常値、リーグ条件が無視されパ・リーグ選手が混入、通算成績らしき数値がシーズン成績として提示、など複数の事実性の問題が同一ケース内に重複していた。
- MT03-Turn1: 実在しないカード（巨人×阪神、2025-06-10）について、実在する別カード（巨人×ソフトバンク）の結果を断りなく提示していた（事実確認はDB直接照会で実施）。

### 想定以上に自然に処理できていたパターン

- B02（「今日の試合結果」というリアルタイム性を要求する質問に対し、対応不可の理由と代替情報源を明確に提示）は、今回のテストの中で唯一「システムの限界を正直に、かつ実用的に伝える」ことに成功していた。
- B04（大谷翔平がデータ対象外である理由を、ハルシネーションなく「対象範囲外」として説明）も、少なくとも誤情報を作り出さなかった点で評価できる。
- B28（「巨人 今年 何勝?」という助詞を省略した口語入力から、チーム名と年をある程度正しく抽出できていた）は、条件抽出の部分だけを見れば意外と頑健だった。ただし、そこから実際の勝敗数を返す動作には繋がっていない。
- MT03-Turn1（試合結果自体の文章生成）は、対象を誤っている点を除けば、得点経過・主な投手・主な打者・主な得点シーンまで含めて非常に読みやすく詳細な文章が生成されており、生成された文章自体のクオリティは高かった。

### 全体としての所感

「NPBの試合結果・選手成績をチャットで聞ける」という触れ込みで初めて使うユーザーを想定すると、今回試した47件中Pass/Partialは合計4件のみで、大半のケースで「聞いたことと違う答えが返ってくる」「答えになっていない」という体験になった。特に深刻なのは、(1) 選手やチームを取り違えたまま、いかにも回答している体裁の文章を返してくる、(2) ランキング等の数値を誤ったまま断定的に提示する、(3) フォローアップ会話で直前の文脈をほぼ引き継げない、の3点で、これらはいずれも「ユーザーが検証しない限り誤情報だと気づけない」タイプの失敗であり、単なる「わかりません」より実害が大きい。一方で、対応範囲外であることを正直に伝えられたケース（B02, B04）や、実在データに基づく試合結果の文章生成自体のクオリティは、うまく機能した場合には十分実用的な水準に見えた。総じて、「対応できる範囲では質が高いが、対応できない／条件抽出に失敗した場合のフォールバックが弱く、しかもそれが多発する」という状態だと思われる。

## 改善案（実装は行っていない）

- 条件抽出・選手名解決に失敗した場合、無関係なデータを返す代わりに「何が分からなかったか」を明示し、聞き返す設計にする。
- ランキング・集計系の回答は、ソート基準・対象期間・対象リーグを結果本文に明記し、内部的にも要求された条件（期間・リーグ）でのフィルタが機能しているか検証する。
- フォローアップ（指示語・省略主語）の文脈引き継ぎを強化し、直前のターンで確定した対象（選手・チーム・試合）を優先する。
- 対応スコープ外（監督・将来予測・他競技等）の質問に対する「対応していません」という明示的な断り文を、B02のように一貫して出せるようにする。
- 存在しない対戦カード等、質問の前提が事実と異なる場合は、黙って近い結果を差し替えるのではなく、前提が誤っている旨を明示する。
