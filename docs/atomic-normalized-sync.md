# 正規化D1の原子的な差分同期

従来の26テーブル全件削除と5,000行単位の再投入は使用しない。
`sync:normalized-d1` は公開済みSQLiteスナップショットと次のデータを比較し、
変更行のINSERT・UPDATE・キー付きDELETEだけを1つのSQLファイルへ出力する。

## 公開手順

1. R2から前回公開済みスナップショットと年別SQLiteを取得する。
2. 公開世代をD1と照合する。初回、または前回の公開成功後にR2保存が失敗した場合はD1 exportから基準を復元する。
3. 年別SQLiteを正規化し、公式補完データをローカル候補に適用する。
4. 辞書IDを既存IDへ対応付け、差分SQLを生成する。未使用の辞書行は維持する。
5. 公開済みスナップショットのコピーでSQL全体をリハーサルする。外部キー、日付、運用整合性、容量を公開前に検証する。
6. **SQLファイル全体を1回だけ** `wrangler d1 execute --remote --file` に渡す。ファイルの分割は禁止する。
7. ファイル先頭で旧公開世代、各UPDATE/DELETEで変更前の行と更新件数を検査する。末尾で新公開世代を記録する。
8. インポート成功後に公開世代を読み返し、検証済みスナップショットをR2へ保存する。

D1 bulk importは失敗時にインポート開始前へ戻る。途中で生成したDELETEだけを
独立実行しない。通信断時は公開世代を照合し、成功応答の喪失と失敗を区別する。
整合性検査・補完を公開後に実行する旧Workflowステップは廃止する。

## 可視性と制約

ローカルでの準備中はD1を変更しない。D1インポート中はCloudflare側が
クエリを受け付けない時間があり得る。無停止を保証する方式ではないが、
削除後・部分投入済みの状態を公開するファイル間の窓はない。
インポート失敗時は旧データ、成功時は完成した新データが残る。
チャットは回答処理の前後で公開世代を照合する。処理途中に公開世代が変わった
場合は混在した回答を返さず、再試行を促す503を返して利用枠を返却する。

公開世代は同期ジョブの競合も検出する。公開DBへの手動書込や別の同期経路は
使用しない。必要な補完処理は候補作成に組み込む。
通常同期ではD1の全件COUNT・外部キー全走査を行わず、候補をローカルで検証する。
初回のD1 exportと、変更量に応じたインポート利用量は別途発生する。
中断から再開する場合、`--normalized-candidate` で保持済みの正規化候補を渡せる。
この場合も年別SQLiteとの件数・業務キー・主要集計の一致を再検証し、補完・差分の
リハーサル・公開前の整合性検査を省略しない。

## 証跡

- `data/logs/d1-sync-normalized/delta.json`: テーブル別変更行数
- `candidate-integrity.json`: 公開前の運用整合性検査
- `backfill.json`: 公開前の補完処理
- `summary.json`: 同期結果
- `published.sqlite`: 公開が確認された候補。R2へ保存する基準スナップショット
- `data/logs/atomic-d1-publication-proof-20260907.json`: 専用D1の失敗時復元試験

仕様: https://developers.cloudflare.com/d1/best-practices/import-export-data/
実装上の失敗時復元案内はWrangler 4.83.0のbulk import処理で確認し、専用D1でも実証した。
